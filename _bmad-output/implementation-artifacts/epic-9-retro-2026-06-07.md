## What went well

1. **bmad-create-ux-design before code** — Vitali aligned UX using a methodology he did not know existed (`bmad-ux`). Output: `ux-design-specification.md`, design direction D1 (Expand Panel), stakeholder-confirmed.
2. **Scoped UX increment** — focus was Dashboard + Notes (hub / browse / work), not a whole-app redesign. Settings received only `DeveloperInfo`; Login and nav unchanged.
3. **Phased implementation** — 6 small phases reduced regression risk vs one large PR.
4. **Shared sort utility** — `sortNotesForDisplay()` eliminated Dashboard vs list order mismatch.
5. **Toast handoff pattern** — `location.state` on navigate to detail avoids toast unmount on list page.
6. **Adversarial code review** — caught 5 real bugs before ship (toast timer reset, scroll RAF cleanup, meQuery guard, lastNote validation, continueTitle fallback).

---

## Challenges and growth areas

1. **Unexpected phase count** — 14 UX workflow steps + 6 implementation phases felt heavy for a solo developer. Root cause: two layers (planning UX vs coding) not distinguished upfront.
2. **UX scope confusion** — unclear whether UX applied to whole app or Notes only. Resolution: UX spec `focusScope: Dashboard + Notes`; other surfaces touched only when UX required it (Settings Developer info).
3. **Fragile persistence patterns** — `sessionStorage` (`last-note`, scroll restore) + `location.state.toast` + Query cache each need separate guards. Most review patches were here.
4. **Documentation lag** — ADR-008 status table was Pending while code shipped; ADR-009 synced better (spec + ADR updated 2026-06-07).
5. **Deferred edge cases** — background refetch overwriting detail form edits; toast replay on bfcache; second navigation to same noteId losing toast state. Logged in `deferred-work.md`.

---

## Key insights

1. **UX in BMad is a scoped increment**, not “redesign everything.” Full 14-step UX for large role changes; shortened UX (scope + flows + 2–3 directions) for P2-sized work.
2. **Workflow order for UX changes:** `bmad-ux` → ADR → spec → code → review. Not code first.
3. **P0/P1/P2/P3 are feature depth, not app generations.** P2 (`?search=`, `returnUrl`) and P3 (tags, pinned) **extend** ADR-008/009; they do not require redoing routing or UX v2.
4. **Quality ≠ repeated code review.** Five layers (planning, phase acceptance, review, automation, release) each need one pass; three review loops do not substitute for e2e.
5. **First formal retrospective** in this project — no Epic 8 retro to compare; lessons from ADR-008 were applied organically (error masking fix, scroll guard, session cache helper).
